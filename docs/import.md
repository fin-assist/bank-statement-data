# Импорт выписок — FIN-342

Реализованы шесть существующих RPC `StatementsService`, `UserSettingsSyncService.SetUserTimezone` и `UserDeletionService.PurgeUserData`. Внешний BFF использует опубликованные контракты `gen/go/v0.5.0`. Публичные API операций и аналитики в эту задачу не входят.

## Приём и повтор запроса

Файл полностью читается до EOF с пределом 10 МиБ; одновременно допускаются четыре буфера. Размер, заявленный в заголовке сверх предела, и фактическое превышение дают некэшируемый `FILE_TOO_LARGE` до обращения к ключу. Заголовок gRPC ограничен 64 КиБ, фрагмент — 256 КиБ. Имя — точные UTF-8 байты клиента, включая пустое имя; NUL и неверный UTF-8 отклоняются. Ограничение 255 символами из старого описания схемы заменено более поздним FIN-297: ни усечения, ни нормализации имени нет. Поле PostgreSQL уже имеет тип `text`.

Идентичность запроса — `SHA256(SHA256(file_bytes) || raw_utf8_filename)`. Ключ проверяется после EOF. Публичный `go-idempotency v0.6.0` хранит принятый результат и известные 422; адаптер переводит отказ формата/банка до классификации результата библиотекой. Повтор с тем же ключом и содержимым возвращает прежний upload_id, другое имя/содержимое — конфликт. Удаление загрузки не освобождает ключ для нового действия. Исходный запрос не получает разрешения повтора из причины ошибки или доменного результата.

Приём удерживает общий session advisory lock отдельного пула (8 соединений). После резервирования весь эпизод ограничен 14 секундами. До облачного PUT короткая транзакция сохраняет приватную строку `staging` с серверным ключом `<user_uuid>/<upload_uuid>`. После подтверждения PUT другая транзакция вместе с результатом ключа переводит её в `processing`. Неизвестный результат COMMIT не считается откатом. Неопределённое намерение остаётся в БД для восстановления; неизвестный исход PUT не повторяется автоматически.

## Обработка и чтение

Два фоновых обработчика поднимают `processing` из PostgreSQL. Сетевое чтение и разбор выполняются вне транзакции. До любых операций над источниками повторно проверяются фактическая длина и SHA-256 прочитанного объекта; несовпадение завершает загрузку ошибкой и стиранием. Под свежим tombstone guard и блокировкой пользователя одна транзакция связывает счета и источники, применяет правила, сохраняет результат, пересчитывает закрытие непрочитанных строк и ставит реальные месяцы в `recalc_queue`. Готовность downstream-аналитики этим не объявляется: доставки или публичного API аналитики здесь нет.

OFX-парсер ограничен 10 МиБ и глубиной 64. Исходные ACCTID/FITID сохраняются по существующей схеме, но не попадают в API, ошибки и логи. Маска счёта добавляется только при проекции. Дата строки — DTPOSTED; отсутствующий/неверный день, неверная сумма и неполная строка дают контролируемые причины и исходный физический номер строки, без её содержимого. Текст NAME ограничен 1000 символами; FITID длиннее 255 считается неполной строкой, а не усечённым идентификатором.

Общий DTSTART/DTEND загрузки применяется ко всем её счетам (решение владельца 26.10.2026); отдельного JSONB периодов нет. При нескольких полных диапазонах используется общий min/max; без диапазона — первая/последняя прочитанная операция. `tbank_ofx.bank_refund=true` в существующем extensions хранит только производный признак буквального MEMO «Возврат», без дополнительного исходного текста. Итоги денежных сумм — только RUB по актуальному calc.md; прочие валюты сохраняются и считаются, но не складываются с рублями и не конвертируются. Это намеренно отличается от старого упрощённого refcalc.

History показывает только `processing`/`done`; `staging`/`failed`/`deleted` скрыты. Watch начинает с текущего состояния и заканчивает подтверждённым результатом либо канонической бизнес-ошибкой плюс совместимым legacy-полем. Ошибка транспорта не превращается в выдуманный результат. `CANCELLED` и `PROCESSING_FAILED` используют общий `google.rpc.Status` без request-retry/wait details.

Настройка часового пояса принимает только более новую версию. Config/History/Unread получают согласованный read-only snapshot с primary. Ссылка экспорта воспроизводит утверждённый browser-session URL из Confluence 11206657; сервис не запрашивает банк и не принимает банковскую сессию. Диапазон вычисляется календарно в часовом поясе профиля, включая 29 февраля.

## Объектное хранилище и удаление

Нужно отдельное приватное ведро Yandex Object Storage с серверным KMS-шифрованием. IAM-токен читается из явно указанного файла при каждом запросе; его обновление выполняется вне сервиса. HTTPS, явный HTTP transport, запрет redirect и 10-секундный предел обязательны. Секреты, имя и содержимое файла не включаются в сообщения ошибок и логи.

**Ведро никогда не должно иметь versioning, Object Lock или правила удаления пустых маркеров.** При запуске до listener сервис проверяет versioning/lifecycle/object-lock. Это не проверка всей IAM/ACL-политики: приватность, чтение только поддержкой, единственный писатель и запрет изменения этих настроек оператором — обязательные deployment-условия. Нужны IAM-права чтения трёх настроек ведра. В этой задаче облачные настройки и deployment не выполнялись.

Исходный PUT использует `If-None-Match:*`. Удаление — подтверждённая безусловная запись зашифрованного пустого объекта с тем же ключом. Пустой технический маркер сохраняется бессрочно: поздний исходный PUT получает 409/412 и не восстанавливает файл. Физического S3 DELETE нет. List пропускает пустые объекты, сохраняя пагинацию, Open пустого объекта означает отсутствие файла.

Purge состоит из двух фаз: сначала коммит tombstone с сохранением всех намерений; затем exclusive advisory lock дожидается писателей, подтверждает пустые маркеры для всех сохранённых ключей и фактических объектов префикса; только после этого отдельная транзакция удаляет персональные строки и ключи идемпотентности. `file_deleted_at` фиксирует подтверждённый маркер и позволяет следующему RPC продолжить после таймаута; для retired-пользователя это допустимо и у приватной staging/processing строки. Ошибка облака оставляет БД для повторного Purge; успех не возвращается преждевременно.

Сборщик убирает зависшие staging и неудачные файлы. Отдельный аудит сирот рассматривает только точные серверные UUID/UUID ключи старше часа, под exclusive lock и свежей проверкой primary; неизвестная форма ключа, ошибка чтения или активная ссылка не разрешают стирание. Отдельный пул барьера не занимает data connection, нужный завершающей транзакции. Неопределённый исход session unlock уничтожает соединение, а не возвращает его в пул.
