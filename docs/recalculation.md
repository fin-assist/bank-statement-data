# Пересчёт, версии определений и исторический бэкфилл (FIN-357, FIN-6)

`metrics-recalculation` каждые 3 секунды выбирает не более 16 пользователей с готовой `recalc_queue`
(round-robin по user_id продолжает обход после полной пачки занятых пользователей)
или пропущенным ежедневным сроком `daily_recalc_due_at`. Перед выборкой тот же worker
планирует не более 16 пользователей исторического бэкфилла; транзакция страницы ограничена 5 секундами. Каждый пользователь получает отдельный
30-секундный бюджет. Tombstone guard ожидается не дольше 100 мс: занятый пользователь пропускается,
остальные продолжают работу. Все снимки строятся из одного committed `Snapshot` под той же
блокировкой пользователя, которую берут импорт, ручные изменения и удаление. Сеть внутри SQL
транзакций не вызывается.

Пересчитывается весь покрытый календарь пользователя: месяцы, содержащие покрытый выпиской день,
и их кварталы/годы. Это консервативный охват всех зависимостей сравнений, наблюдений и исторических
баз; покрытые периоды без операций также публикуются. Формулы остаются в `calculating`, справочник —
в `accounting`. FIN-6 использует этот же конвейер для исторической эволюции определений.

Источники постановки очереди — существующие импорт, закрытие/повторное открытие непрочитанных строк,
удаление загрузки, смена категории/разделение пары, dismissal/restore и смена пояса. Ежедневный срок
задаётся `accounting.NextDailyAfter` с единственным config `DAILY_RECALCULATION_OFFSET` (обычно 00:05),
по IANA-поясу пользователя с учётом DST и пропущенных дат. Пропущенный при остановке срок остаётся
готовым после перезапуска. Следующий срок назначается после успешной атомарной публикации.

## Версии и завершение

Пользовательская очередь сначала публикует `recalculating=true` отдельной транзакцией и новой
`calc_version`. Сбой до расчёта оставляет эту отметку и очередь для следующего экземпляра. Ежедневный
пересчёт и очередь только смены определений (`registry_only=true`) не включают признак действия пользователя.
При объединении с пользовательской правкой обычная запись сбрасывает `registry_only=false`.
`metrics_publication.recalculating` хранит внутренний признак начатой работы, а
`pending_user_action` — с каким публичным признаком уже отправлено начало. Если после тихого
начала пришла пользовательская правка, публикуется новый `recalculating=true` до восстановления
покрытия и расчёта; повторные попытки и перезапуск не создают ещё один такой маркер. Успешный
расчёт сбрасывает оба служебных признака.

Успешный расчёт в одной транзакции:

1. Сохраняет неизменяемые protobuf запросы и события `statement.metrics_calculated` через go-outbox.
   Два режима каждого периода всегда в одном запросе; размер — до 4 МиБ, разбиение только между
   периодами. Для всех частей одна версия и идентичное глобальное состояние.
2. Записывает полный перечень идентификаторов календарных периодов в `metrics_publication.period_keys`:
   пары `Kind` (`month`, `quarter`, `year`) и `Key` (`YYYY-MM`, `YYYY-Qn`, `YYYY`), например
   `{"Kind":"month","Key":"2026-09"}`. Исчезнувшие периоды, в том числе после смены пояса
   и удаления последней загрузки, передаются как `removed_periods` для обоих режимов.
3. Сохраняет финальное state-only `recalculating=false` со следующей версией. Его доставка ждёт
   подтверждения всех частей предыдущей версии через `metrics_delivery`: порядок работы outbox
   не может преждевременно снять признак пересчёта.
4. Продвигает `user_state.calc_version`, удаляет обработанную очередь и назначает следующий daily срок.

Версии — PostgreSQL integer/int32, без переполнения и переиспользования. Новая запись не может
войти до commit; затем она ставит новую очередь, поэтому изменения во время расчёта не теряются.
Неуспех откатывает весь набор. Backoff очереди — 1, 2, 4… до 300 секунд, `last_error` содержит только
`calculation_failed`; обновляются лишь захваченные поколения, новый импорт сохраняет свой reset. Ежедневный срок не
обходит backoff существующей пользовательской очереди. Daily-only сбои имеют отдельный durable
счётчик с той же экспонентой 1,2,4…300 секунд; возраст первой ошибки сохраняется независимо
от следующего срока. Успех или новая пользовательская запись сбрасывают daily retry metadata.
Восстановление после 30-секундного дедлайна имеет отдельный 5-секундный бюджет при живом lifecycle.

## Outbox и удаление

`PEER_ANALYTICS_ADDR` обязателен при сборке, включая dev. Вызов — системный
`MetricsIngestService.UpsertUserMetrics`, только сервисный токен, дедлайн 30 секунд. Доставщик
использует отдельный primary pool на 4 соединения для LISTEN, claim, fanout и наблюдения.
Чтение финансового payload, проверка барьера и ACK используют основной `a.DB` вместе с расчётами;
при конкуренции они могут ждать свободное соединение в пределах дедлайна доставки, затем повторяются.
Основной pool уже проверяет доступность primary при запуске.
Источники миграций: tombstone, idempotency, outbox, затем service.

Финансовые protobuf payload хранятся только в `metrics_delivery` под каскадным FK на пользователя.
Общий outbox содержит `google.protobuf.StringValue` с непрозрачным UUID доставки и такой же `event_key`;
в нём нет user_id, сумм, названий и иных финансовых фактов. После RPC success payload удаляется,
повтор ссылки без payload подтверждается без RPC. Tombstone проверяется при чтении payload с primary.
Purge каскадно стирает payload и перечень периодов атомарно с user_state. Даже поздний fanout из
оперативной памяти outbox может вернуть лишь непрозрачную ссылку, не удалённые финансовые данные.
Получатель analytics независимо применяет свои tombstone/version guards.

Метрики go-outbox показывают число/возраст записей и ошибки по фиксированному target `analytics`.
Обязательный алерт `finassist_outbox_oldest_age_seconds > 3600` распространяется и на неразложенные
события. Ошибки worker журналируются фиксированным `calculation_failed`, без пользовательских меток.

## Исходные границы покрытия и смена пояса

Новые импорты сохраняют исходные моменты `DTSTART`/`DTEND` (источник `tags`) либо моменты первой
и последней прочитанной операции (`operations`). Календарные дни заново строятся в текущем поясе
профиля. Дата без времени в OFX сохраняет принятую парсером семантику полуночи +03:00; смещение,
явно указанное в OFX, сохраняется в исходном моменте. Например, операция 01.09.2026 00:30 +03:00
без тегов покрытия после перехода на America/Havana покрывает 31 августа: прежний сентябрьский
ключ удаляется и оба августовских режима публикуются вместе.

У загрузок до FIN-357 остались только SQL DATE. Перед расчётом `covering.Service` восстанавливает
**только исходные границы** из сохранённого OFX: до 16 файлов за попытку, исходный размер и SHA256
проверяются, используется прежний parser. Загрузка объекта и parsing выполняются вне SQL; затем
отдельная короткая транзакция получает tombstone guard и user lock и записывает metadata только
при совпадении user/upload/key/size/hash и по-прежнему `status=done`. Каждая загрузка сохраняет
прогресс отдельно, поэтому сбой после нескольких файлов не заставляет читать их заново.

Операции, категории, непрочитанные строки, сохранённый результат импорта и правила не переписываются.
Это восстановление утраченной provenance, не исторический бэкфилл определений FIN-6. Неизвестный
период не подменяется первой/последней нынешней операцией: DTSTART/DTEND могли включать пустые дни.
Отсутствующий или повреждённый оригинал оставляет явную retry-ошибку, очередь и pending state;
успешный пересчёт/финальное false до восстановления всего покрытия не публикуются. Завершившееся
удаление загрузки или пользователя делает поздний IO no-op: CAS и tombstone не дают вернуть metadata.

Откат бинаря сохраняет additive schema. Down 000007 отказывается удалять существующий перечень
опубликованных периодов или ожидающие payload: их потеря нарушила бы долговечную доставку и
removed_periods после повторного обновления. Пустая схема проходит up → down → up.

## Измерение вычислений

`BenchmarkFIN357ThirtyYearCalendar` вызывает настоящий coordinator с 30 годами покрытия и двумя
наборами: пустой файл либо 100 операций в месяц (36 000 фактов). На Intel i7-9750H 2.60 GHz:
до изменения заполненный набор не завершался за budget 30 с; CPU-профиль показывал 60% в
повторных `calendar.bounds`. После `calculating.Prepare` и одного хронологического индекса:
пустой набор — 0,353 с, заполненный — 0,812 с. Это измерение чистого расчёта/сборки набора,
без PostgreSQL, сериализации и сети; произвольно большой календарь им не доказывается.

`Prepare` один раз проверяет факты и строит календарь/индекс; `Prepared.Build` сохраняет прежние
формулы и фильтры, но выбирает операции по полуинтервалу через двоичный поиск. Исходный snapshot
не меняется, все opaque references по-прежнему разрешаются при Build в транзакции вызывающего.

```sh
go test -timeout=120s ./internal/recalculating -run '^$' \
  -bench '^BenchmarkFIN357ThirtyYearCalendar$' -benchtime=1x -count=1
```

## Ревизии исходных данных (FIN-369)

Вторая транзакция пересчёта читает counters categories/uploads и settings_version пояса под той же
блокировкой пользователя, которая защищает факты до commit. Этот vector закрепляется в State,
передаётся во все month/quarter/year snapshots обоих режимов и сохраняется в immutable bytes
metrics_delivery. Любое глобальное изменение ревизии заменяет весь опубликованный календарь,
включая финансово не изменившиеся периоды. Только состояние финального ACK содержит source vector:
он доказывает полноту всего набора. Clearing-состояние и состояния всех chunks опускают vector.
Повтор одной calc_version не переоценивает
счётчики при доставке: sender читает сохранённые bytes, а не текущее source state.

Прежние факты и их ревизии сохраняются в metrics_publication.state JSON (`data_revisions`),
но mandatory pending/clearing-состояние в wire опускает весь vector. Это относится и к daily-only,
у которого user-facing recalculating=false. Delivery ждёт ACK clearing перед любым chunk;
final ждёт ACK всех частей и clearing, включая публикацию без частей. Новый ещё не доставленный
месяц и навигация поэтому не могут получить ложное подтверждение полноты. Internal started
отделён от user recalculating: последний зависит от пользовательской очереди, не от daily или доставки.
Отсутствие metadata у legacy остаётся unknown,
текущие counters в прежние снимки не подставляются. Сохранённый JSON проверяется строго: null внутри
map, дроби, bool, отрицательные/overflowed значения не становятся известным нулём.

Если хоть одна использованная done-загрузка имеет statement_range_source=NULL, uploads неизвестен:
его code опускается в tools и primary GetDataVersion. После bounded OFX repair тот же counter снова
доступен новым ответам; metadata repair не изменяет финансовые факты и не повышает uploads_revision.
Удалённые, processing и failed загрузки не создают это ограничение.

Проверки: TestUnitRecalculationSourceRevisionsPreservePendingAndReplaceWholeCalendar,
TestUnitPublicationSourceRevisionsAreImmutableAcrossEveryPairAndFinalState,
TestUnitPublicationRequiresClearingAckBeforePartsAndFinal,
TestUnitRevisionDecodeRejectsNullAndPreservesExactCounters; независимый component integration
TestIntegrationProducerDailyRepairRebuildsAllHeadersAndGatesProofOnDurableACKs собирает
координатор, репозитории, publisher и delivery с настоящим PostgreSQL и фейком удалённого RPC,
проверяет durable ACK-barrier и immutable payload без app.New. API-сценарий
TestAPISourceRevisionProducerRebuildsWholeCalendarAndRepairsUnknownCoverage проходит
два месяца и оба режима, category, daily-triggered source repair без изменения source counters,
удаление последней загрузки. Пояс отдельно проверяет сценарий RecalculationImportEditTimezoneDeletionAndDurableDelivery.


## Выпуск определений и запуск бэкфилла (FIN-6)

Реестр остаётся в коде `internal/accounting`: `Definitions()` задаёт пары `metric_id` и
`definition_version`, `CatalogVersion()` — монотонное поколение выпуска, `CatalogFingerprint()` —
детерминированный SHA-256 состава определений и параметров общих правил. При добавлении или
изменении метрики увеличиваются её версия и поколение каталога; при изменении общего правила —
версии всех затронутых метрик и поколение. Финансовые формулы меняются отдельной задачей.
Результат `calculating.Metric` сохраняет версию определения при вычислении; `metricswire`
передаёт именно её, а не подменяет версией текущего каталога. `calc_version` остаётся независимой
монотонной последовательностью публикаций пользователя.

После `migrate up` и запуска нового бинаря worker автоматически начинает новый обход. Оператору
не нужно выставлять пользовательские версии или выполнять массовый UPDATE истории. В
`metrics_backfill` хранится административная контрольная точка выпуска: поколение, fingerprint,
курсор обхода и число просмотренных пользователей. Это не реестр определений и не признак
готовности данных отдельного пользователя. Завершение обхода означает постановку работы,
а не доставку в analytics; завершение расчёта видно по очереди, доставки — по outbox.

Каждая страница под общей блокировкой выпуска получает tombstone guard и блокировку пользователя,
ставит все исторические месяцы в существующую `recalc_queue` с `registry_only=true` и атомарно
сохраняет курсор. Она учитывает покрытие без операций и ранее опубликованные месяцы. Неполученная
за 100 мс блокировка tombstone откатывает страницу: её повторят без пропуска пользователей.
Уже существующая очередь сохраняет причину, поколения, возраст и backoff; пользовательская
правка имеет приоритет. После commit курсора перезапуск продолжает со следующей страницы;
повтор страницы безопасен. Новые импорты всегда ставят обычную очередь и рассчитываются текущим кодом,
включая пользователей, чей UUID оказался перед курсором. После окончания обхода курсор очищается.

Снимки до замены остаются видимы целиком (FIN-196). Бэкфилл не включает публичный
`state.recalculating`, не меняет исходные операции и не использует снимки других периодов для
межмесячных расчётов. Старый набор каждого периода атомарно заменяется парой обоих режимов в одном
UpsertUserMetrics через прежние payload/outbox/ACK-барьеры FIN-357/369. Ошибки используют имеющийся
экспоненциальный backoff очереди 1–300 секунд; purge удаляет её и payload каскадом, tombstone не
позволяет позднему обходу их восстановить.

Планирование и расчёт берут общую блокировку выпуска до tombstone/user locks. Бинарь с меньшим
поколением не рассчитывает после регистрации большего; завершённый обход сначала проверяется
обычным чтением и не берёт исключительную блокировку, поэтому тик другой реплики не ждёт
долгий текущий расчёт. Перед каждой публикацией сохраняется shared-проверка поколения.
Бинарь с тем же номером и иным fingerprint даёт ошибку,
а не смешивает правила. Нельзя менять правила без увеличения поколений. При первом переходе с
бинарей до FIN-6 их worker нужно остановить до запуска нового: они ещё не знают этой блокировки.
После регистрации нового поколения откат к меньшему требует исправляющего выпуска с новым
большим поколением; откат версии определения назад не публикуется.

Проверка оператора (только чтение, в БД bank-statement-data):

```sql
SELECT catalog_version, fingerprint, planned_users, finished_at
FROM metrics_backfill ORDER BY catalog_version DESC LIMIT 1;
SELECT registry_only, count(DISTINCT user_id) AS users, min(enqueued_at) AS oldest,
       max(attempts) AS retries
FROM recalc_queue GROUP BY registry_only;
```

`finished_at IS NULL` — обход ещё идёт, даже если очередь временно пуста. Если процесс был остановлен,
достаточно запустить тот же бинарь; для недоступного соседа восстанавливается только доставка.
Для намеренного повторного обхода того же неизменного выпуска после устранения причины оператор
останавливает worker всех экземпляров, удаляет только его checkpoint и снова запускает их:

```sql
DELETE FROM metrics_backfill WHERE catalog_version = :current_catalog_version;
```

Очередь, финансовые payload и версии пользователя при этом не очищаются. Это административный
повтор, не способ переиспользовать поколение с изменёнными правилами. При ошибке fingerprint нужен
корректный новый выпуск. Деплой, такие операторские SQL и перезапуски выполняются отдельно от PR.

Наблюдаемость: `finassist_definition_backfill_planned_users` показывает просмотренных пользователей,
`finassist_definition_backfill_pending_users` — пользователей с registry-only очередью,
`finassist_definition_backfill_failed_users` — из них имеющих повторные ошибки,
`finassist_definition_backfill_oldest_age_seconds` — возраст самой старой такой очереди.
Смешанная пользовательская очередь учитывается общими `finassist_recalculation_*`; состояние
доставки — `finassist_outbox_*`. Метрики не имеют пользовательских labels. Рост failed/age требует
проверки доступности PostgreSQL, исходных OFX и analytics, а не ручного удаления очереди.
