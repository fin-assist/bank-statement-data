# Инструменты помощника (FIN-358)

`AssistantToolsService` реализует четыре существующих RPC contracts с provenance из FIN-367:
`GetDataOverview`, `AggregateOperations`, `FindOperations`, `GetDataVersion`. Системная таблица
доступа разрешает только проверенный `assistant`; `user_id` явно передаёт доверенный сосед.
Пользовательский authorization не определяет субъекта и не заменяет сервисную идентичность.

`operations.Tools` использует тот же потоковый selector, проекцию публичных записей и
`accounting.Classify`, что пользовательский поиск: свои переводы исключены, режимы переводов
совпадают, RUB-возврат уменьшает целевую категорию. `AggregateOperations` требует transfer_mode;
неизвестные измерения, повторы измерений, более двух измерений и несовместимые фильтры
отклоняются. Суммы/средние считаются целыми числами с проверкой переполнения, среднее — с
округлением половины от нуля. Группы отсортированы по абсолютной сумме со стабильным разрешением
равенства ключами; limit 1–200 (default 50). Общие суммы/счётчики считают всю выборку, truncated
показывает только отброшенные группы.

Готовый фильтр каждой группы сохраняет исходный поиск, диапазон, суммы и финансовый режим,
сужает месяц/категорию/продавца. All-time переход содержит фактический диапазон, поэтому публичный
поиск не подставляет последний год. Merchant UUID не кодирует описание. Пустое описание имеет
отдельный долговечный ключ и текст «Без описания». `s_regular_all` при merchant-группировке
превращается в точный `s_regular_UUID`, сохраняя правила наблюдения; остальные специальные
выборки сохраняют эквивалентное пересечение фильтров.

`FindOperations` удерживает максимум100 элементов (default20), но просматривает все совпадения
для точного total_count; это отдельное назначение, публичный поиск по-прежнему отказывает при
более10000 результатов. Порядок — новые первыми либо большие суммы первыми, затем время/UUID.
Ответ использует безопасную списочную проекцию без полного номера счёта, описаний деталей,
MCC/posted_at и spoken-текста счета.

Обзор и bounds используют календарь калькулятора и покрытие `DTSTART..DTEND`, а не наличие
операций в месяце. Полностью покрытый месяц с нулём операций отличается от `COVERAGE_NO_DATA`.
Отдельный компактный PostgreSQL projection читает последний момент операции каждого дня:
этого достаточно для точного `bounds.data_to`, без загрузки всего ledger в память. Поля,
не поставляемые текущим OFX-источником (cashback, MCC, отдельный posted_at), не объявляются
доступными. Пустые даты/версии остаются неизвестными, а не заменяются текущим временем.

Обзор, агрегаты и операции вместе со своими версиями читаются в едином repeatable-read snapshot
по штатной primary/replica маршрутизации. `GetDataVersion` читает последнюю ревизию с primary
отдельным запросом, независимо от metadata; запаздывающая реплика не скрывает committed изменение
от истории помощника. Системная модель сама по себе не проверяет request.user_id через
interceptor: tools явно проверяют uncached primary tombstone до и после чтения. Guard и
сетевые вызовы внутри read transaction не используются. Read RPC никогда не создаёт ссылку.

Для этого `SaveRules` атомарно создаёт недостающие merchant/regular UUID при записи импорта;
миграция000008 заполняет прежнюю историю, сохраняя все существующие ID и dismissal. Наличие
строки regular_payment само по себе не признаёт операцию подпиской — распознавание по-прежнему
проверяет общие окна/пороги и dismissal. Исходный `categories_changed_at` включает категорию и «Не подписка»; новый `uploads_changed_at`
монотонно меняется при успешном импорте/удалении в той же транзакции. Эти timestamps сохраняются
для совместимости; сравнение с `calculated_at` не даёт строгой гарантии при конкурентном commit.
Для исправления FIN-367 добавляет provenance ревизий (открытые коды): `categories` и `uploads`
— независимые bigint счётчики committed изменений; `time_zone` — проверенная `settings_version`.
Значения не зависят от часов и меняются атомарно вместе с финансовыми фактами. Пустой новый
пользователь имеет известные нулевые значения. Старые данные получают начальную baseline, а
прежние ответы без сохранённого provenance не получают выдуманную историю ревизий: FIN-368
отмечает их `unverified`. Метаданные ответа относятся к его snapshot; последующее сравнение с
current primary revision обнаруживает и commit, начавшийся до чтения старого snapshot.
Очистка файлов/расчёт счётчики не меняют, удаление последней загрузки версии не теряет.

После включения ответов с revision provenance нельзя возвращать пишущие сервисы к сборке,
которая не обновляет счётчики, и считать историю подтверждённой: старая сборка не знает новых
инвариантов. Откат такой выкладки требует отдельного плана признания provenance неизвестным.
Миграционный backfill не восстанавливает неизвестные коммиты прежней сборки.

Проверки: unit — независимые суммы/округление, обе стороны возвратов, лимиты, переполнение,
ошибки и tombstone; integration — прямые компоненты Tools/ToolFacts, импортные транзакции
и PostgreSQL, отдельный gRPC-адаптер с настоящим сервисом без app.New: точные суммы/переходы,
более10000 строк, coherent snapshot при concurrent commit, primary/replica и tombstone
после чтения. API — полная production-сборка с реальным PG18 и публичным gRPC: все
группировки, до первого расчёта, оба режима, пустой охват, версии/повторы/удаление, caller
и tenant isolation. RPC и provenance заданы
утверждённым контрактом FIN-367; сервис использует опубликованный SDK v0.6.0, локальный replace не
попадает в PR. Новых REST-полей и настроек окружения нет. Worker/доставка — FIN-357,
историческая эволюция определений — FIN-6.

Если у использованной done-загрузки `statement_range_source IS NULL`, первичное покрытие
ещё не подтверждено. Overview, Aggregate, Find и primary GetDataVersion опускают только
`uploads` revision; categories/time_zone сохраняются. Чужие, удалённые и незавершённые загрузки не делают эту provenance неизвестной. После bounded OFX recovery FIN-357
новое чтение снова получает прежний uploads counter: metadata repair счётчик не продвигает.
Прежний ответ с неполной baseline остаётся `unverified`, текущая metadata его не дополняет.
Проверки: `TestUnitToolFactsReadOnlyProjectionAndStorageFailures`,
`TestAPIAssistantRevisionsOmitUnverifiedRawCoverage` и независимый
`TestIntegrationToolsPrimaryVersionsAndLegacyCoverageKnownness`.
