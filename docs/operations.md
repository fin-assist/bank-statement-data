# Операции, категории и «Не подписка» (FIN-356)

Production assembly регистрирует `OperationsService` (ListFeed/SearchOperations/GetOperation/ChangeCategory),
`CategoriesService.ListCategories` и оба метода `RegularPaymentsService`. Вызывает только `bank-bff` с
пользовательской identity; admission проверяет primary tombstone. HTTP-маршруты остаются FIN-359.

`internal/operations` владеет сценариями и проекцией строк; `internal/adapter/grpc/operations` проверяет
транспорт и переводит ошибки через finerr; `internal/adapter/postgres/operations*.go` читает и сохраняет
факты. `App.Operations` — та же сборка для интеграционных тестов. Новых контрактов и миграций нет.

## Чтение

Один repeatable-read snapshot на replica, либо primary при доверенном `x-read-primary`. Лента берёт три
календарных месяца, заканчивая месяцем последней публичной записи (у пары — списание), и проверяет cursor
как начало месяца профиля. Глобальное устаревание определяется покрытием завершённых выписок, включая
пустые; сводки используют `calculating.InspectMonth` и общий `FinancialRow` в режиме `with`.

Поиск по умолчанию охватывает `[сегодня − 12 месяцев; завтра)` с календарным clamp 29 февраля.
Явная одна граница остаётся открытой; `all_time` убирает период, но несовместим с границами. Raw cursor
PostgreSQL отдаёт одну публичную запись или пару за раз. Go сохраняет максимум 10001 совпадение, после
чего возвращает `TOO_MANY_RESULTS`; редкий текстовый поиск по большой истории также не копирует историю
в память. SQL сортировка/агрегация ограничена PostgreSQL `work_mem` с возможностью spill. Запрос ограничен
30 секундами RPC и caller context. Порядок — время, затем ID по убыванию.

Текстовый поиск проверяет обе исходные стороны пары, итоговую/банковскую категорию, точную денежную сумму
без float и маски обоих счетов. `transfer_mode` применяет сохранённые итоговые/возвратные категории через
общий `FinancialRow`; усечённый период не пересчитывает цель возврата без его исторического списания.

UUID selection разрешается по `user_id`; описание не кодируется в токене. `s_merchant_<UUID>` — общее
точное описание, с направлениями и возвратами по фильтрам. `s_small_merchant_<UUID>` — отдельная непрозрачная
выборка наблюдения: только расходные операции с едиными исключениями. Калькулятор теперь выпускает её
для мелких трат, чтобы generic merchant не расширял цифру на возврат или перевод. После обновления
производителя следующие снимки содержат точный токен; пересчёт старых снимков — конвейер FIN-357/FIN-6.

Для `s_regular_all` окно распознавания — последние полные месяцы до `filter.to` включительно (при
отсутствии `to` — до текущего месяца); сами списания отбираются в исходных границах поиска. Это сохраняет
готовые переходы месяца/квартала/года. SQL собирает только массивы размером не больше окна каталога, а
`RegularGroup` принимает решение общей медианой/допуском. Для `s_small_category` статистика групп берётся
за полные затронутые гражданские месяцы, затем применяются исходные точные границы. `SmallGroup` общий
для поиска и калькулятора. Даты не зашиты в selection.

Детали ищутся сначала по точному `(user_id, occurred_at, id)`, затем по `(user_id, id)`; у пары ID и время
списания, скрытая сторона по её raw ID недоступна. Точность PostgreSQL сохраняется в protobuf Timestamp.
Каталог — три системные категории и категории банка из текущих source пользователя; известный порядок
берётся из `sort_order`, новый — из минимального `source_record.id`, как описано в `schema.md`.

## Запись

Guard tombstone → user row lock → чтение всей истории → общий `importing.ApplyRules` → `SaveRules` и
очередь → `categories_changed_at` в одной транзакции. Полная история нужна для целей возвратов и
сохранения/разделения/сборки пар; сетевых RPC внутри транзакции нет. При разделении обе стороны получают
`is_split`, выбранная категория — подходящей стороне, другая — категория банка. У пары manual всегда
false. Повторный импорт сохраняет ручные факты; одинаковое присваивание не меняет версию.

Dismiss/restore присваивают `dismissed_at` устойчивого regular UUID. Идемпотентный повтор не двигает
очередь/версию. Реальное изменение ставит все месяцы операций и покрытия в существующую `recalc_queue`,
включая зависимые месяцы возвратов и наблюдений; это консервативная постановка без пропуска зависимостей.
Месяцы очереди вычисляются как гражданские ключи, не как потенциально отсутствующая местная полночь.
Уникальные ключи передаются параметром одним `INSERT … SELECT unnest(text[])` с приведением к `date`;
каждый месяц повышает generation один раз, с прежним wrap32767→1 и сбросом attempts/last_error.
`categories_changed_at` монотонен с точностью PostgreSQL даже при двух изменениях в одну микросекунду.
Ежедневный сдвиг задаёт переменная `DAILY_RECALCULATION_OFFSET` в формате `time.ParseDuration`: по умолчанию
`5m` (обычно 00:05 по поясу пользователя, исходное правило `grpc-api.md` §7.3), допускается `0 <= offset < 24h`.
Это прошедшая длительность от первого реального начала локальных суток (`StartOfDay`), а не фиксированное время на часах: при переходе DST длительность может
дать другое местное время. `0` означает начало суток и не подменяется значением по умолчанию; пустая/отсутствующая
переменная использует `5m`. Некорректное значение останавливает запуск до открытия ресурсов.
Конфигурация читается только в `config`, затем `app` явно передаёт значение в репозитории для всех путей
импорта/удаления/смены пояса/правки/отметок. Существующее разрешение отсутствующей полуночи/даты через
`StartOfDay`/`AddDays` сохранено. `accounting.NextDailyAfter` выбирает ближайший строго будущий срок:
календарный день определяется по `now - offset`, затем перебираются начала следующих реальных дат.
Поэтому повторная постановка после полуночи короткого дня DST сохраняет ещё будущий срок предыдущей даты;
при точном совпадении срока выбирается следующий. Исторический обратный переход через полночь
может вернуть уже прошедшее начало следующей даты — такой кандидат пропускается. Коды типов счетов и их общие названия задаёт `domain/accounts.go`;
OFX, import wire и публичная проекция используют прежние наборы поддерживаемых случаев и fallback.
Worker, версия расчёта, outbox и доставка остаются FIN-357; они здесь не симулируются.

## Проверки

Unit проверяет правила, финансовые фильтры, группы, ошибки и ограниченную потоковую выборку. Integration
проверяет PostgreSQL, повторный импорт, обе стороны пары, зависимый возврат, версии, конкуренцию и purge;
отдельно — настоящий SDK/серверный транспорт. Ошибки очереди/версии на реальном PostgreSQL откатывают
категории, отметки, поколения очереди и версию вместе. Каузальная гонка правки с повторным импортом
наблюдает ожидания user row и Guard advisory lock, проверяя оба порядка без sleep. API вызывает все семь RPC полной сборки, включая ошибки,
identity и существующие чужие UUID выборок/категории, большие редкие выборки и лимит. Настройка проверяется сквозь реальную сборку и PostgreSQL для импорта, правки, dismiss/restore, смены пояса и удаления; календарные тесты покрывают default/zero/10m, большие сдвиги через полночь короткого дня, точную границу, DST, обратные переходы через полночь и пропущенные/повторённые даты. Все три statements-порога независимо ≥80%.
Сквозная доставка и реальный stage остаются FIN-357/FIN-362.

FIN-358: непрозрачный `s_small_category_merchant_<UUID>_<category>` — пересечение остатка
категории с точным owned merchant. Общий selector сохраняет исходное expense-направление,
категорию и whole-month SmallGroup; возвраты не добавляются в переход. Токен не содержит
периода и клиент переносит его без разбора, как любой selection. Проверки: независимые unit,
PostgreSQL component и API small-category merchant drilldown, включая несколько месяцев.
