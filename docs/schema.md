# Схема БД

Схема сервиса — `migrations/000001_init.up.sql` ([FIN-111](https://finassist.youtrack.cloud/issue/FIN-111)); обоснование решений, альтернативы и открытые вопросы — в описании PR #2. Смысл полей — `fin-assist/contracts` (`docs/api.md` 3–6, `docs/grpc-api.md` 7.2–7.3, `docs/calc.md`).

## Что держит схема

Решение владельца 19.10.2026: в БД нет правил валидации и логики.

- **Остаются:**
  - `PRIMARY KEY`, `UNIQUE` (включая частичные уникальные индексы) и `FOREIGN KEY` вместе с каскадами;
  - `NOT NULL` и `DEFAULT`;
  - партиционирование `operation` и его границы.
- **Не используются:**
  - `CHECK` и `EXCLUDE`;
  - триггеры и хранимые функции;
  - домены с ограничениями и генерируемые колонки как обход этого правила.
- DDL миграций (например, `DO`-блок, создающий партиции) — не логика: он выполняется один раз при деплое.

Ключами схема держит:

- `user_id` — первая колонка каждого первичного и уникального ключа данных пользователя. Каждый FK между таблицами пользователя включает `user_id`: строка не может сослаться на чужой счёт, загрузку или операцию. `TestForeignKeysBetweenUserTablesIncludeUserID` проверяет это по каталогу для всех FK, включая будущие.
- Удаление пользователя — `DELETE FROM user_state`: каскад FK доходит до каждой таблицы пользователя.
- Дедупликация: `source_record (user_id, account_id, external_id)`; счёт — `account (user_id, source, ext_id_hmac)`.
- Загрузки записи источника — массив `source_record.upload_ids` (решение владельца в ревью FIN-111, вместо таблицы связи): операция живёт, пока хотя бы у одной её записи массив не пуст. FK у массива нет — что в нём только загрузки того же пользователя, держит код.
- Пара перевода — значение `operation.transfer_pair_id` у двух её сторон (решение владельца в ревью FIN-111, вместо таблиц `transfer_pair` и `transfer_pair_member`). «Одна операция — не больше одной пары» следует из того, что колонка одна; остальные правила пары держит код (ниже). Поиск сторон — по индексу `(user_id, transfer_pair_id)`.
- Один файл — одна загрузка: `UNIQUE (user_id, object_key)`.
- Стабильный id регулярного платежа: `regular_payment (user_id, periodicity, description)`. Продавец для токена выборки: `merchant (user_id, key)`.
- «Нет данных» ≠ 0: `monthly_agg` ссылается на `month_state` — сумм за месяц без покрытых дней не бывает.
- Одна текущая версия определения метрики: частичный уникальный индекс `metric_definition_current_idx`.

## Ожидаемые запросы

### `source_record.upload_ids`

- **Удаление загрузки (api.md 3.5)** — в одной транзакции под блокировкой пользователя:
  1. `UPDATE source_record SET upload_ids = array_remove(upload_ids, $upload) WHERE user_id = $user AND upload_ids @> ARRAY[$upload]`;
  2. `DELETE FROM operation` — операции пользователя, у которых есть запись с пустым массивом и нет записи с непустым (каскадом уходят их записи; у второй стороны пары код очищает `transfer_pair_id`);
  3. `DELETE FROM source_record WHERE user_id = $user AND upload_ids = '{}'` — записи с пустым массивом у оставшихся операций (другой источник).
- **Закрытие строки по `FITID` (FIN-79, api.md 3.6, правило 1)** — запись по уникальному ключу `(user_id, account_id, external_id)` и проверка `$upload = ANY(upload_ids)`: строку закрывает только загрузка, в файле которой есть операция.
- **Импорт** — повтор записи добавляет загрузку в массив: `upload_ids = array_append(upload_ids, $upload)`, если её там ещё нет.
- **Индекс на `upload_ids` не нужен.** Шаг 1 идёт по префиксу `user_id` первичного ключа — тысячи записей одного пользователя, фильтр по массиву по ним дешёвый, а удаление загрузки редкое. GIN по одному `upload_ids` искал бы поперёк пользователей, а составной `(user_id, upload_ids)` требует расширения `btree_gin`. Вернёмся к индексу, если замер покажет нужду.
- Запросы проверяет `TestUploadDeletionByUploadIDs` (`migrations/schema_test.go`).

## Инварианты в коде сервиса

Всё, что ниже, раньше было `CHECK` в черновике схемы и теперь проверяется кодом. Как код это обеспечивает:

- **Один путь записи.** Каждую таблицу пишет один репозиторий (`internal/adapter/postgres`). Значения он получает из типов домена (`internal/domain`), а не из сырых строк и чисел. Правило проверяет конструктор или метод типа — один раз и в одном месте. Ручных `INSERT`/`UPDATE` в обход репозитория нет.
- **Тесты.** У каждого правила — юнит-тест типа домена: допустимые и недопустимые значения. Интеграционный тест репозитория на PostgreSQL проверяет, что записанное читается тем же типом. Строку, нарушающую правило, код не пишет, а при чтении считает ошибкой данных: лог и алерт, без паники и без молчаливой подмены.
