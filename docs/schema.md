# Схема БД

Схема сервиса — `migrations/000001_init.up.sql` ([FIN-111](https://finassist.youtrack.cloud/issue/FIN-111)); известные категории банка — `migrations/000002_known_categories.up.sql` ([FIN-200](https://finassist.youtrack.cloud/issue/FIN-200)): 51 категория из `fixtures/calc/categories.json` в `fin-assist/contracts`, в порядке файла, `sort_order` 40–540 после системных (10, 20, 30). `user_state.settings_version` — `integer` с `migrations/000003_settings_version_integer.up.sql` ([FIN-207](https://finassist.youtrack.cloud/issue/FIN-207)); в `000001` он был `smallint`. Обоснование решений схемы, альтернативы и открытые вопросы — в описании PR #2. Смысл полей — `fin-assist/contracts` (`docs/api.md` 3–6, `docs/grpc-api.md` 7.2–7.3, `docs/calc.md`).

## Что держит схема

Решение владельца 19.10.2026: в БД нет правил валидации и логики.

- **Остаются:**
  - `PRIMARY KEY`, `UNIQUE` (включая частичные уникальные индексы) и `FOREIGN KEY` вместе с каскадами;
  - `NOT NULL` и `DEFAULT`;
  - партиционирование `operation` и его границы.
- **Не используются:**
  - `CHECK` и `EXCLUDE`;
  - триггеры и хранимые функции;
  - домены с ограничениями и генерируемые колонки как обход этого правила.
- DDL миграций (например, `DO`-блок, создающий партиции) — не логика: он выполняется один раз при деплое.

Ключами схема держит:

- `user_id` — первая колонка каждого первичного и уникального ключа данных пользователя. Каждый FK между таблицами пользователя включает `user_id`: строка не может сослаться на чужой счёт, загрузку или операцию. `TestIntegrationForeignKeysBetweenUserTablesIncludeUserID` проверяет это по каталогу для всех FK, включая будущие.
- Удаление пользователя — `DELETE FROM user_state`: каскад FK доходит до каждой таблицы пользователя (порядок `PurgeUserData` и tombstone — раздел «Удаление пользователя и tombstone»).
- Дедупликация: `source_record (user_id, account_id, external_id)`; счёт — `account (user_id, source, ext_id)`, номер счёта (`ACCTID`) хранится как есть (решение владельца в ревью FIN-111). `source_record` — отдельная несекционированная таблица, а `operation` остаётся секционированной по годам (решение владельца в ревью FIN-111: «Оставляем таблицу»). Перенести ключ в `operation` нельзя: каждый `UNIQUE` секционированной таблицы обязан включать ключ секционирования `occurred_at`, а `(…, external_id, occurred_at)` не ловит повтор, у которого сменилась дата (холд → проведение, в том числе через границу года).
- Загрузки записи источника — массив `source_record.upload_ids` (решение владельца в ревью FIN-111, вместо таблицы связи): операция живёт, пока хотя бы у одной её записи массив не пуст. FK у массива нет — что в нём только загрузки того же пользователя, держит код.
- Счета загрузки — массив `upload.account_ids` (решение владельца в ревью FIN-111, вместо таблицы `upload_account`). FK у массива нет; счета отдельно от пользователя не удаляются (только purge, вместе с загрузками), поэтому висячих ссылок не бывает, а что в массиве только счета того же пользователя, держит код.
- Пара перевода — значение `operation.transfer_pair_id` у двух её сторон (решение владельца в ревью FIN-111, вместо таблиц `transfer_pair` и `transfer_pair_member`). «Одна операция — не больше одной пары» следует из того, что колонка одна; остальные правила пары держит код (ниже). Поиск сторон — по индексу `(user_id, transfer_pair_id)`.
- Один файл — одна загрузка: `UNIQUE (user_id, object_key)`.
- Стабильный id регулярного платежа: `regular_payment (user_id, periodicity, description)`. Продавец для токена выборки: `merchant (user_id, key)`.
- **PostgreSQL — не хранилище кэша** (решение владельца в ревью FIN-111: «Postgres не должен быть хранилищем кэша. Считаем на лету, если будут проблемы добавим кэш, но не в постгресе»). В схеме нет предрасчитанных агрегатов и кэшей: таблиц `month_state` и `monthly_agg` нет. Помесячные суммы, покрытие и группировки — `ListFeed`/`SearchOperations`, `AssistantToolsService` (`GetDataOverview`, `AggregateOperations`) и пересчёт метрик для `analytics` — считаются на лету из `operation` и периодов загрузок. Если замер покажет нужду в кэше, он появится вне PostgreSQL. «Нет данных» ≠ 0 — правило расчёта: месяц без покрытых дней (calc.md 4) — «нет данных», а не ноль.
- Реестр метрик и правил (FIN-6, docs/calc.md 7) с версиями — в коде, не в схеме (решение владельца в ревью FIN-111: таблиц `metric_definition` и `user_metric_version` нет). Признака «пользователь посчитан по такой-то версии реестра» тоже нет ([FIN-196](https://finassist.youtrack.cloud/issue/FIN-196)): при смене реестра метрики не скрываются, прежний снимок периода виден, пока его целиком не заменит новый. Релиз, который меняет реестр, ограниченными страницами ставит месяцы всех пользователей в `recalc_queue` (строки ниже), и снимки заменяются по мере пересчёта. `metrics_backfill` хранит только административный прогресс обхода выпуска (FIN-6); пользовательской версии реестра в схеме нет.

- **Время в строках** (решение владельца в ревью FIN-111). Общего `updated_at` нет нигде: без триггеров его пришлось бы ставить коду в каждом `UPDATE`, и одно забытое место дало бы неверное значение, а читать его некому. Хранится только время событий, которое кто-то читает (`finished_at`, `deleted_at`, `file_deleted_at`, `dismissed_at`, `categories_changed_at`). В каждой таблице, куда строки попадают по событиям, есть время создания с `DEFAULT now()`: `created_at`, у `upload` — `uploaded_at`, у `recalc_queue` — `enqueued_at`; его ставит база. В справочнике `category` оно необязательно. Правило проверяет `TestIntegrationTimestampsFollowTheRule`.

## Ожидаемые запросы

### `source_record.upload_ids`

- **Удаление загрузки (api.md 3.5)** — в одной транзакции под блокировкой пользователя:
  1. `UPDATE source_record SET upload_ids = array_remove(upload_ids, $upload) WHERE user_id = $user AND upload_ids @> ARRAY[$upload]`;
  2. `DELETE FROM operation` — операции пользователя, у которых есть запись с пустым массивом и нет записи с непустым (каскадом уходят их записи; у второй стороны пары код очищает `transfer_pair_id`);
  3. `DELETE FROM source_record WHERE user_id = $user AND upload_ids = '{}'` — записи с пустым массивом у оставшихся операций (другой источник).
- **Закрытие строки по `FITID` (FIN-79, api.md 3.6, правило 1)** — запись по уникальному ключу `(user_id, account_id, external_id)` и проверка `$upload = ANY(upload_ids)`: строку закрывает только загрузка, в файле которой есть операция.
- **Импорт** — повтор записи добавляет загрузку в массив: `upload_ids = array_append(upload_ids, $upload)`, если её там ещё нет.
- **Индекс на `upload_ids` не нужен.** Шаг 1 идёт по префиксу `user_id` первичного ключа — тысячи записей одного пользователя, фильтр по массиву по ним дешёвый, а удаление загрузки редкое. GIN по одному `upload_ids` искал бы поперёк пользователей, а составной `(user_id, upload_ids)` требует расширения `btree_gin`. Вернёмся к индексу, если замер покажет нужду.
- Запросы проверяет `TestIntegrationUploadDeletionByUploadIDs` (`migrations/schema_test.go`).

### Категории банка пользователя (5.1)

Отдельной таблицы нет (решение владельца в ревью FIN-111: «у нас уже есть таблица категорий»). У пользователя есть только категории из его выписок (решение владельца 20.10.2026, FIN-199): справочник 5.1 — системные категории из миграции и категории банка его операций; известная категория, которой нет в его выписках, в справочник не попадает. Список известных категорий задаёт только направление и порядок:

```sql
SELECT c.id
FROM category c
LEFT JOIN (
    SELECT o.bank_category_id AS id, min(r.id) AS first_record
    FROM source_record r
    JOIN operation o ON o.user_id = r.user_id AND o.occurred_at = r.operation_occurred_at AND o.id = r.operation_id
    WHERE r.user_id = $1
    GROUP BY o.bank_category_id
) u ON u.id = c.id
WHERE c.is_system OR u.id IS NOT NULL
ORDER BY c.sort_order NULLS LAST, u.first_record
```

- **Порядок** (calc.md 10) — системные и известные категории по `sort_order`, затем новые категории банка (`sort_order IS NULL`) в порядке первого появления.
- **Порядок первого появления** — наименьший `source_record.id` (identity) среди записей с этой категорией. Импорт вставляет записи в порядке строк файла, импорты одного пользователя фиксируются по очереди под его блокировкой: так получается «по загрузкам, внутри файла — в порядке строк» (calc.md 10).
- **Отклонения от calc.md 10:**
  - загрузки упорядочены по моменту фиксации импорта, а не по `uploaded_at`: две загрузки, которые разбирались параллельно и завершились не по порядку, дадут порядок завершения;
  - после удаления загрузки категория, у которой не осталось операций, из списка уходит, а порядок остальных считается по оставшимся загрузкам.
- План: записи пользователя по префиксу `user_id` первичного ключа `source_record`, операции — по их первичному ключу. Отдельный индекс не нужен.
- Запрос проверяет `TestIntegrationBankCategoriesInOrderOfFirstAppearance`.

### Период выписки и закрытие строк (api.md 3.6, правила 2–3)

Период выписки — один на файл: `upload.statement_from`/`statement_to` (решение владельца в ревью FIN-111: у счетов одного файла периоды совпадают). Какие счета есть в загрузке — массив `upload.account_ids` (решение владельца в ревью FIN-111, вместо таблицы `upload_account`): все блоки `STMTTRNRS` файла, в том числе счёт без операций.

**Почему `date`, а не `timestamptz`.** `DTSTART`/`DTEND` — календарные дни выписки: «период 1–25 сентября», `DTEND` без времени покрывает свой день целиком (api.md 3.6). Если хранить их как момент (`timestamptz`) и переводить в пояс профиля, у пользователя западнее смещения файла (`+03`) день сдвигается назад: `2026-09-25 00:00+03` в `Europe/Kaliningrad` — это 24 сентября, и последний день периода теряется. Перевод «в смещении файла» тоже возможен, но `timestamptz` само смещение не хранит, его пришлось бы держать отдельной колонкой. Поэтому адаптер берёт дату так, как она записана в файле (если у `DTSTART`/`DTEND` есть время — только его дату в смещении файла), и пишет её в `date`. С ней сравнивается день операции или строки в поясе профиля: `(occurred_at AT TIME ZONE user_state.timezone)::date BETWEEN statement_from AND statement_to`.

- **Правило 2** (строка без `FITID`, с датой): строку счёта A закрывает более поздняя загрузка, у которой счёт A есть в `account_ids` (`account_id = ANY(u.account_ids)`) и период `statement_from..statement_to` покрывает день строки: день строки — в поясе профиля, границы периода — даты из файла, `statement_to` покрыт целиком.
- **Правило 3** (без даты и без `FITID`): новая загрузка со счётом A, чей период покрывает весь период старой загрузки.
- Загрузки берутся по префиксу первичного ключа `upload (user_id, …)` — их у пользователя десятки, поэтому ни отдельный индекс, ни GIN по `account_ids` не нужны.
- **Отклонение от формулировки api.md 3.6** («период выписки по тому же счёту»): сравнивается период файла. Пока периоды счетов в файле совпадают, результат тот же.

### История загрузок (3.4)

- Период загрузки в истории — период выписки `statement_from..statement_to` (решение владельца в ревью FIN-111; контракт меняется в [FIN-197](https://finassist.youtrack.cloud/issue/FIN-197)). Если в файле нет `DTSTART`/`DTEND`, период считается на лету по дням первой и последней операции загрузки: `min/max(occurred_at)` операций, у записей которых в `source_record.upload_ids` есть эта загрузка, — дни в поясе профиля.
- Сводка 3.4 (`summary.first_operation_at`/`last_operation_at`) — первая и последняя операция пользователя, тоже на лету по `operation`.

### Версия данных для помощника (`GetDataVersion`)

- `categories_changed_at` хранится в `user_state`: последнюю ручную смену категории или отметку «не подписка» из других данных не восстановить (снятие отметки и удалённые вместе с загрузкой правки следа не оставляют).
- `uploads_changed_at` не хранится (решение владельца в ревью FIN-111): это `max(greatest(finished_at, deleted_at))` по загрузкам пользователя в статусах `done` и `deleted`. Загрузки удаляются только логически, поэтому удаление след оставляет; запрос идёт по префиксу `user_id` первичного ключа `upload`.

### Запись по `occurred_at` и `id` (api.md 4.2, 4.3)

Контракт — [FIN-202](https://finassist.youtrack.cloud/issue/FIN-202) ([fin-assist/contracts#24](https://github.com/fin-assist/contracts/pull/24), `gen/go` v0.4.0): `GetOperation` и `ChangeCategory` получают вместе с `id` записи её `occurred_at` из ленты или поиска, поле обязательное (grpc-api.md 7.2, «Запись по `occurred_at` и `id`»). Время записи может измениться (холд проведён, выписка загружена повторно), поэтому неверное время — промах, а не ошибка (решение владельца 20.10.2026: «Поле обязательное, но промах обрабатывается»).

ID записи — `operation.id` одиночной операции или `transfer_pair_id` пары `own_transfer`; время пары — время списания (api.md 4.1). Сторона пары записью не является. Поэтому оба запроса ищут по одному условию на `id`:

1. **Точный ключ** — одна секция года:

   ```sql
   SELECT … FROM operation
   WHERE user_id = $1 AND occurred_at = $2
     AND ((id = $3 AND transfer_pair_id IS NULL) OR transfer_pair_id = $3)
   ```

   Секции отсекаются по `occurred_at = $2`: со значениями параметров — при планировании, у подготовленного запроса с generic-планом (кэш запросов pgx) — при старте выполнения. Внутри секции работают первичный ключ `(user_id, occurred_at, id)` и частичный `operation_transfer_pair_idx`.
2. **0 строк — промах**, поиск по `id` во всех секциях:

   ```sql
   SELECT … FROM operation
   WHERE user_id = $1
     AND ((id = $2 AND transfer_pair_id IS NULL) OR transfer_pair_id = $2)
   ```

   Параметры свои: `$2` — ID записи. Номера параметров не переносятся из запроса 1, потому что PostgreSQL не подготовит запрос с пропущенным `$2`, тип которого не выводится.

   Каждая секция проверяется по своим частям `operation_user_id_id_idx (user_id, id)` и `operation_transfer_pair_idx (user_id, transfer_pair_id)`: по одной пробе на секцию (сейчас 18). В ответе — текущий `occurred_at` найденной записи, клиент обновляет по нему строку ленты.
3. **0 строк и здесь** — `NOT_FOUND`.

Правила:

- **Доступ.** `$1` — пользователь вызова (`reqctx.UserID`). Оба запроса ограничены `user_id`, поэтому чужой `id` даёт 0 строк в обоих. Ответ тот же `NOT_FOUND`, что для несуществующего ID: что чужая запись есть, не подтверждается.
- **Момент, а не строка.** `$2` — `timestamptz`, `+03:00` и `Z` одного момента совпадают. Сравнение точное, до микросекунды хранения: значение, округлённое клиентом, — промах, и ответ даёт шаг 2.
- **Сторона пары и разделённая пара.** Условие `transfer_pair_id IS NULL` у ветки `id` делает так, что `id` операции, которая стала стороной пары, — `NOT_FOUND` (api.md 4.2: «пара … собрана»). У разделённой пары значение очищено у обеих сторон: ID пары — `NOT_FOUND`, стороны снова находятся по своим `id`.
- **Пара.** Точный ключ находит одну сторону — ту, чьё время передано (это время списания из ленты). Вторую код дочитывает по `(user_id, transfer_pair_id)` через `operation_transfer_pair_idx` (`TestIntegrationTransferPairLookup`). Промах находит сразу обе стороны.
- **Сколько строк.** Схема не держит уникальность `id` во всех секциях: `UNIQUE` секционированной таблицы обязан включать `occurred_at`. Больше одной строки у одиночной операции или больше двух у пары — ошибка данных (строка в «Инвариантах в коде сервиса»).
- **4.2** читает через `db.Reader(ctx)`: реплику или primary по `x-read-primary`.
- **4.3 — не одна команда `UPDATE`.** Новую категорию нужно проверить по `assignable` и `kinds` против направления найденной записи, а для пары решить, разделяется ли она. Поэтому сначала запись читается, затем пишется (правила — api.md 4.3, calc.md 3.2–3.5). Всё — в одной транзакции `db.Run` на primary:
  1. блокировка пользователя (`FOR NO KEY UPDATE` на `user_state`), как у импорта и удаления загрузки: до конца транзакции время записи не меняется, поэтому `FOR UPDATE` на строках операций не нужен;
  2. поиск записи запросами 1–2;
  3. `UPDATE operation SET … WHERE user_id = $1 AND occurred_at = $2 AND id = $3` — по полному первичному ключу каждой найденной строки с её текущим `occurred_at`: одна секция на строку. Колонки правил (`category_id`, `manual_category_id`, `refund_target_category_id`, `is_split`, `transfer_pair_id`) пишутся вместе. Пару, которая собирается из операции с категорией «Между своими счетами», код тоже пишет так: вторую сторону он находит по правилам calc.md 3.2;
  4. `user_state.categories_changed_at` (`GetDataVersion`) и пометка месяцев затронутых строк в `recalc_queue` — месяцы в поясе профиля.

  `source_record` не меняется: ручная категория хранится в `operation.manual_category_id`, а ключ (счёт, `FITID`) из calc.md 3.4 — это запись источника, по которой повторный импорт находит ту же операцию. `items` ответа — записи после изменения с их текущим `occurred_at`.
- Запросы проверяет `TestIntegrationOperationLookupByOccurredAtAndID` (`migrations/schema_test.go`). Он проверяет:
  - точный ключ читает одну секцию — по плану `EXPLAIN` с параметрами и по generic-плану подготовленного запроса;
  - промах проходит по частям обоих индексов в каждой секции;
  - после переноса операции в секцию следующего года (холд проведён) старый ключ даёт 0 строк, а промах находит запись с новым `occurred_at`;
  - чужой `id` не находится ни одним запросом;
  - запись 4.3 по полному ключу читает одну секцию;
  - пара находится по своему ID, а стороны пары по своим `id` не находятся.

## Удаление пользователя и tombstone

Контракт — `fin-assist/contracts`: `docs/grpc-api.md` 7.1 (`DeleteAccount`, «Tombstone в каждом сервисе данных»), 6 (`PurgeUserData`: повтор — OK), 6.1 (получатель outbox для удалённого пользователя отвечает OK без действий), `proto/finassist/userdeletion/v1`. `PurgeUserData` вызывает только `user` из своего outbox (системная модель) и повторяет до OK ([FIN-201](https://finassist.youtrack.cloud/issue/FIN-201)).

### Где хранится отметка

- Таблица библиотеки `go-tombstone` ([FIN-110](https://finassist.youtrack.cloud/issue/FIN-110)) в БД сервиса: строка (`user_id`, `deleted_at`) на удалённого пользователя (proto `userdeletion`). Миграции — источник библиотеки в `MigrationSources()` перед источником сервиса, со своей таблицей версий ([migrations.md](migrations.md), «Источники: сервис и библиотеки»).
- FK на `user_state` у отметки нет: она переживает удаление строки пользователя. Срок хранения контракт не задаёт («сервис помнит `user_id`»).
- Состояние на 25.10.2026 (FIN-267): подключён `go-tombstone v0.1.0` — таблица `tombstone_users(user_id uuid PRIMARY KEY, deleted_at timestamptz NOT NULL)` с версиями в `tombstone_schema_migrations`, источник первым в `MigrationSources()`; admission go-grpc отвечает удалённому `TOKEN_REVOKED`. `Store.Guard` и `Store.Purge` (`PurgeUserData` ниже) подключаются с первыми пишущими RPC. Отметку ставит `Purge` библиотеки (идемпотентно), ключ — UUID в каноническом виде.

### Что делает `PurgeUserData`

1. Одна транзакция `db.Run`:
   - отметка — вставка с `ON CONFLICT DO NOTHING`; ставится и для пользователя, которого сервис не знал (нет `user_state`), чтобы опоздавший `SetUserTimezone` не создал его;
   - `DELETE FROM user_state WHERE user_id = $1` — каскад FK удаляет `account`, `upload`, `operation` (все партиции), `source_record`, `unread_line`, `regular_payment`, `merchant`, `recalc_queue`.

   Общий справочник `category` (без `user_id`) не меняется: категории банка, появившиеся из выписок пользователя, остаются в нём. Таблицы библиотек (outbox, идемпотентность) каскад не задевает (открытый вопрос FIN-201).
2. После коммита — файлы: листинг префикса `<user_id>/` в Object Storage (по страницам) и удаление каждого найденного объекта. По префиксу, а не по строкам `upload`: строк уже нет, и так находится файл без строки (сбой между PUT и INSERT).
3. Ответ OK — когда данных пользователя нет ни в таблицах сервиса, ни в хранилище. Строки таблиц библиотек (outbox `UpsertUserMetrics`, записи идемпотентности) после OK пока остаются — это отклонение от `userdeletion.proto` («OK означает, что данных пользователя в сервисе больше нет»), открытый вопрос FIN-201.

Ошибка на любом шаге — ошибка вызова, outbox `user` повторит. Повтор проходит те же шаги: отметка уже есть, `DELETE` удаляет 0 строк, листинг добирает оставшиеся файлы. Файлы удаляются после коммита: с этого момента новая загрузка не создаст строку `upload` (ниже), поэтому листинг видит все файлы, у которых могла быть строка.

### Как записи не возвращают данные

Инвариант: **строка `user_state` есть ⇒ отметки нет.** Его держат два правила:

- `PurgeUserData` ставит отметку и удаляет `user_state` одной транзакцией;
- строку `user_state` создаёт одна функция репозитория (`INSERT … ON CONFLICT DO NOTHING`) и в той же транзакции **после** вставки проверяет отметку: есть — откат, вызывающему — «пользователь удалён».

Остальные записи ссылаются на `user_state` по FK, а шаги пользователя берут его строку `FOR NO KEY UPDATE`. Поэтому для них проверка в той же транзакции — эта блокировка или FK:

- purge закоммичен раньше — блокировка не находит строку, вставка дочерней строки падает на FK (SQLSTATE 23503), ничего не пишется;
- запись взяла блокировку или прошла FK раньше — `DELETE` purge ждёт её коммита и каскадом удаляет и то, что она записала.

Код читает «нет строки `user_state`» и 23503 по FK на `user_state` как «пользователь удалён», а не как сбой: в вызове от имени пользователя — `TOKEN_REVOKED`, в системном вызове — OK без действий, в фоновом задании — конец работы без повтора и алерта.

Исключение — гонка создания: если строки `user_state` ещё не было, `DELETE` purge не ждёт чужую незакоммиченную вставку. Как сериализовать этот случай — открытый вопрос FIN-201.

| Путь записи | Удалённый пользователь |
|---|---|
| Вызов от имени пользователя (`UploadStatement`, `DeleteUpload`, `ChangeCategory`, `Dismiss/RestoreRegularPayment`, …) | интерцептор отвечает `TOKEN_REVOKED` до обработчика ([server.md](server.md), шаг 8). Вызов, начавшийся до purge, останавливает транзакция записи |
| `UploadStatement` (поток до 60 с) | `upload` (и при первой загрузке `user_state`) создаётся в транзакции по правилам выше; удалён — `TOKEN_REVOKED`, временный объект удаляется. Временный объект лежит тоже под префиксом `<user_id>/`, иначе purge его не найдёт |
| Разбор и импорт (до 3 мин) | транзакция импорта берёт блокировку `user_state`; строки нет — импорт ничего не пишет, файл удаляется. Проверка разборов старше 3 мин и задание добора файлов работают по строкам `upload` — после purge их нет |
| Пересчёт метрик (`recalc_queue`, `daily_recalc_due_at`) | строки очереди ушли каскадом. Пересчёт, начатый до purge, увеличивает `calc_version` под блокировкой `user_state` и в той же транзакции пишет строку outbox `UpsertUserMetrics`; строки нет — нет ни версии, ни строки outbox |
| Outbox `UpsertUserMetrics`, записанный до purge | строка в outbox сервиса остаётся (таблица библиотеки) и доставляется в `analytics`: там его tombstone (OK без действий) или запись, которую удалит его `PurgeUserData` (открытый вопрос FIN-201) |
| Входящий `SetUserTimezone` (порядок с `PurgeUserData` не гарантирован, grpc-api.md 6.1) | создаёт или меняет `user_state` той же функцией; отметка есть — OK без действий |
| `AssistantToolsService` (системные чтения) | данных нет; запись `merchant` для токена выборки не проходит FK |
| Повтор `PurgeUserData` | OK, шаги выше |

## Инварианты в коде сервиса

FIN-356: ручные изменения и dismiss/restore выполняются под тем же user row lock и tombstone Guard, что импорт. `SaveRules` сохраняет целостные пары/цели возвратов и ставит все месяцы операций и покрытия в очередь; `categories_changed_at` изменяется только при реальном присваивании и монотонен на микросекунду. Проверки — `TestIntegrationOperationLedgerSelectionsEditsAndReferences`, `TestIntegrationOperationPairBoundariesAndDerivedRefundScheduling`, `TestIntegrationOperationEditDeleteConcurrencyAndCoherentRouting` и соответствующие API-тесты. Схема не меняется.


Всё, что ниже, раньше было `CHECK` в черновике схемы и теперь проверяется кодом. Как код это обеспечивает:

- **Один путь записи.** Каждую таблицу пишет один репозиторий (`internal/adapter/postgres`). Значения он получает из типов домена (`internal/domain`), а не из сырых строк и чисел. Правило проверяет конструктор или метод типа — один раз и в одном месте. Ручных `INSERT`/`UPDATE` в обход репозитория нет.
- **Тесты.** У каждого правила — юнит-тест типа домена: допустимые и недопустимые значения. Интеграционный тест репозитория на PostgreSQL проверяет, что записанное читается тем же типом. Строку, нарушающую правило, код не пишет, а при чтении считает ошибкой данных: лог и алерт, без паники и без молчаливой подмены.

Партиции `operation` — не ограничение-валидатор, а хранение. Операция вне всех партиций (нет партиции на год) роняет вставку с SQLSTATE 23514 — это сигнал создать партицию (FIN-193), а не правило данных.

FIN-342 добавляет приватный статус `staging`: короткая транзакция сохраняет намерение до любого облачного PUT; история и parser-worker его не показывают. Подтверждённый PUT переводит staging в processing в транзакции результата ключа. Неизвестный исход остаётся для восстановления; структура таблиц не меняется. Общий период DTSTART/DTEND применяется ко всем счетам загрузки (решение владельца 26.10.2026), без account_periods JSONB. Удаление в хранилище теперь означает бессрочный зашифрованный пустой маркер: подробности и условия ведра — [import.md](import.md).

## Публикация метрик и удаление (FIN-357)

`metrics_publication` — контрольная точка: последнее вычисленное `calculating.State`, полный перечень
идентификаторов календарных периодов и признак уже зафиксированного начала пересчёта. Состояние
не означает подтверждённую доставку в analytics; маркер начала позволяет возобновить работу без его повтора.
Каждый элемент `period_keys` —
пара `Kind` (`month`, `quarter`, `year`) и `Key` (`YYYY-MM`, `YYYY-Qn`, `YYYY`), например
`{"Kind":"quarter","Key":"2026-Q3"}`; один идентификатор охватывает оба режима переводов.
Перечень сохраняется после удаления исходных фактов или смены пояса, чтобы удалить исчезнувшие периоды
через `removed_periods`. `metrics_delivery` хранит неизменяемый `UpsertUserMetricsRequest` под непрозрачным
UUID до подтверждения analytics; неподтверждённые части удерживают ACK-барьер финального состояния. Обе таблицы
ссылаются на `user_state` с `ON DELETE CASCADE`; SQL-правил значений/триггеров нет.

В общем outbox финансовые данные не хранятся: только protobuf `StringValue` с UUID доставки и
такой же `event_key`. Поэтому даже поздний fanout после purge оставляет безопасную ссылку,
которую доставщик подтверждает без RPC, когда FK-owned payload уже отсутствует.

Инварианты в коде сервиса:

| Правило | Где соблюдается | Проверка |
|---|---|---|
| Факты, версии, перечень периодов и события фиксируются одной транзакцией под user/tombstone lock | `recalculating.Service`, `postgres.Recalculations` | unit транзакций/ошибок, real-PG/API импорт/правка/пояс/удаление |
| Версия int32 растёт, одна версия ключа не меняет содержимого | `Recalculations.Start/Complete`, immutable `metrics_delivery` | unit exhaustion/CAS, API повторная публикация |
| Оба режима периода находятся в одной части ≤4 МиБ | `metricswire.publications` | unit pair/chunk/oversize guards |
| Финальный false ждёт ACK всех частей предыдущей версии | `metricswire.Delivery`, `DeliveryPending` | unit и API blocked peer |
| Финансовые payload каскадно удаляются с пользователем; поздние ссылки не воспроизводят bytes | FK, `LoadDelivery`, `Delivery` | PostgreSQL/API purge и поздняя доставка |
| Неуспех сохраняет очередь, backoff не перетирает новую generation | `Recalculations.Fail` | unit SQL и PostgreSQL concurrency/recovery |

`upload.statement_from_instant/statement_to_instant` сохраняют первичные моменты покрытия;
`statement_range_source` различает `tags`, `operations`, `none` и прежнюю неизвестную provenance NULL.
При чтении календарные дни строятся из точных моментов в текущем поясе. Старые DATE не преобразуются
в выдуманные исходные instants: bounded metadata repair восстанавливает их из оригинального OFX
с SHA/size, status/object CAS и tombstone guard — [recalculation.md](recalculation.md).

Daily-only ошибки хранят `user_state.daily_recalc_attempts` (0…32767, увеличение с насыщением)
и `daily_recalc_failed_since` (первый неисполненный срок). `Recalculations.Fail` переносит срок
на 1,2,4…300 секунд, не меняя исходный возраст ошибки. Очередь пользовательских изменений имеет
приоритет: пока её строки существуют, expired daily не обходит их `next_attempt_at`; это проверяет
и поиск кандидатов, и locked admission прямого Recalculate. `Complete` и новая пользовательская
постановка сбрасывают обе retry-колонки. PG-тесты проверяют gating, экспоненту, cap, age и reset.

## Источники инструментов помощника (FIN-358)

Миграция `000008_tool_merchant_refs` добавляет `user_state.uploads_changed_at`, `categories_revision`
и `uploads_revision` (bigint NOT NULL DEFAULT0) и заполняет timestamp максимумом
`finished_at/deleted_at` завершённых/удалённых загрузок. Отсутствующие UUID `merchant` и месячных
`regular_payment` заполняются из прежних операций; существующие UUID и dismissal сохраняются.
Существующий timestamp даёт начальную revision1, его отсутствие —0; `time_zone` проецируется из `settings_version`.
Откат удаляет новые timestamp/counters, созданные долговечные ссылки сохраняет: прежний калькулятор
работает с ними без изменения схемы. Обратная миграция не удаляет пользовательские или финансовые факты.

| Инвариант в коде сервиса | Проверка |
| --- | --- |
| Успешный импорт/удаление загрузки продвигают `uploads_changed_at` в той же транзакции; одинаковая микросекунда и откат часов дают прежнее значение +1 мкс. Ошибки/cleanup/расчёт значение не меняют; удаление последней загрузки timestamp не теряет | `TestAPIAssistantToolsRealSourcesAndExactSelections`, `TestIntegrationAssistantToolsRealSourcesAndExactSelections` |
| `SaveRules` создаёт отсутствующие ссылки одним fixed upsert на каждый вид под прежней блокировкой пользователя, до commit; не заменяет UUID/dismissal; SQL ограничен tenant | те же сценарии: готовые переходы сразу после импорта, повторный импорт, dismiss/restore, удаление и возврат данных |
| Системные tools проверяют primary tombstone до и после routed read snapshot, не создают `user_state`, ссылки или финансовые данные | те же сценарии + `TestUnitToolValidationErrorsAndAdmission` |

Строгий provenance (FIN-367/FIN-368): `categories_revision +=1` вместе с ручной категорией,
разделением пары и dismiss/restore; `uploads_revision +=1` вместе с successful Complete/Remove.
Повтор без фактического изменения не увеличивает значение; ошибка/rollback откатывает и факт,
и revision. Отрицательное хранимое значение не уходит в wire; переполнение bigint отклоняет
транзакцию. `settings_version` остаётся единственным счётчиком пояса. Проверки:
`TestIntegrationToolRevisionsCommitAtomicallyAndSurviveClockRollback` и API tools scenarios.
Сборка, не знающая этих инвариантов, не допускается как прозрачный rollback после включения
revision-aware ответов; нужен отдельный план признания provenance неизвестным.

При `statement_range_source IS NULL` у done-загрузки tools не заявляют известный uploads revision.
Условие читается с тем же financial snapshot; current GetDataVersion использует primary независимо
от read hints. Metadata recovery восстанавливает известность без изменения source counters;
failed/processing/deleted и чужие загрузки не создают неизвестность. Это проверяют unit и реальные
API/integration `AssistantRevisionsOmitUnverifiedRawCoverage`.

FIN-369 хранит source vector в существующем metrics_publication.state JSON (data_revisions), без
новой SQL-миграции. Legacy отсутствие остаётся unknown; source counters из user_state читаются
под user-lock в той же транзакции, что полный календарь фактов и immutable metrics_delivery.
Новые periodpairs обоих режимов и final ACK получают один source vector; состояния chunks и
mandatory clearing опускают metadata до финального ACK всех частей. Stored State сохраняет
metadata прежнего состояния до Complete. Проверки и инварианты — [recalculation.md](recalculation.md).
