# Миграции и работа с БД

Решение — [FIN-115](https://finassist.youtrack.cloud/issue/FIN-115), Confluence «Архитектура» → «Миграции и доступ к БД».

- Runner — [`go-migrate v0.1.0`](https://github.com/fin-assist/go-migrate/tree/v0.1.0), использующий golang-migrate и pgx/v5. Сервис задаёт источники, CLI, logger и таймауты явно.
- Запросы — ручной SQL на `pgx/v5`, без ORM и генерации кода.
- Линтер миграций — [squawk](https://squawkhq.com) в CI.

## Файлы

- `migrations/NNN_name.up.sql` и `migrations/NNN_name.down.sql`, номера с `000001`, имя — строчные латинские буквы, цифры и `_`.
- **Down-файл обязателен** для каждой версии. Шаг, который нельзя откатить (удаление столбца или таблицы с данными), всё равно получает down-файл: первая строка — `-- irreversible`, дальше явная ошибка с объяснением. Проверка «вверх → вниз → вверх» такой шаг только применяет.

  ```sql
  -- irreversible
  DO $$ BEGIN RAISE EXCEPTION '000012_drop_legacy_column is irreversible: restore from backup'; END $$;
  ```

- Применённая миграция не меняется: исправление — новым файлом. CI отклоняет PR, который меняет, переименовывает или удаляет существующий файл в `migrations/`.
- Файлы вшиты в бинарь (`migrations/embed.go`), отдельной папки на сервере не нужно.

## Как выполняется файл

golang-migrate отправляет файл целиком одним запросом. PostgreSQL выполняет такой запрос **как одну неявную транзакцию**: если упала любая команда, откатывается весь файл (проверяется PostgreSQL-тестами библиотеки go-migrate). Поэтому:

- `BEGIN; … COMMIT;` в файле не нужен — файл и так атомарен.
- **`CREATE INDEX CONCURRENTLY` и `DROP INDEX CONCURRENTLY` — одной командой в отдельном файле.** Внутри транзакции они запрещены, а с другой командой в том же файле транзакция будет. Если `CONCURRENTLY` упал, остаётся индекс в состоянии `INVALID`: его удаляют (`DROP INDEX CONCURRENTLY IF EXISTS …`) и запускают снова. Поэтому в таких файлах — `IF NOT EXISTS` / `IF EXISTS`.
- **Параметры сессии — только `SET LOCAL`.** Обычный `SET` переживает транзакцию и действует на следующие файлы того же запуска.

## Таймауты

Команда `migrate` ставит на соединение `lock_timeout` и `statement_timeout` и ограничивает ожидание параллельного запуска того же источника: переменные `MIGRATE_LOCK_TIMEOUT`, `MIGRATE_STATEMENT_TIMEOUT`, `MIGRATE_WAIT_TIMEOUT`, значения по умолчанию — в [config.md](config.md), «`migrate`» (таблица генерируется из кода).

Долгая миграция (бэкфилл, индекс на большой таблице) поднимает таймаут у себя: `SET LOCAL statement_timeout = '2h';`. Повторять таймауты в каждом файле не нужно — поэтому правила squawk `require-lock-timeout` и `require-statement-timeout` выключены в `.squawk.toml`.

Упал по `lock_timeout` — значит, таблицу держала долгая транзакция сервиса. Файл откатился целиком, его можно запустить снова (после `force`, см. ниже).

## Запуск

```
bank-statement-data migrate up                        # все источники по порядку
bank-statement-data migrate version                   # версии; (dirty) — упавшая миграция
bank-statement-data migrate down <source> <steps>     # откат последних шагов одного источника
bank-statement-data migrate force <source> <version>  # выставить версию и снять dirty, SQL не выполняется
```

Нужна `DB_PRIMARY_DSN` — DSN primary, роль сервиса. Миграции никогда не идут на реплику.

- **Прод** — Job k3s с командой `migrate up` до раскатки Deployment (манифесты — `fin-assist/infra`). Под при старте миграции не запускает.
- **Стенд** — скрипт деплоя запускает `migrate up` перед перезапуском сервиса под systemd.

Поведение одинаковое. Два запуска одновременно (повторённый Job, Job и скрипт) не мешают друг другу: второй ждёт первого на отдельной advisory-блокировке источника, затем видит, что всё применено. Отдельная блокировка нужна потому, что `lock_timeout` ограничивает и ожидание advisory-блокировки самого golang-migrate — без неё второй запуск падал бы через 5 секунд. Конкурентные запуски проверяют PostgreSQL-тесты go-migrate; сервис не содержит копию runner.

## Источники: сервис и библиотеки

Библиотеки с таблицами (идемпотентность FIN-78, outbox FIN-109, tombstone FIN-110) приносят свои миграции. У каждой — **своя таблица версий**, поэтому номера библиотеки и сервиса не пересекаются. Источники перечислены в `internal/app/wire.go` (`MigrationSources()`) и применяются по порядку: сначала библиотеки, затем сервис. Миграции сервиса могут ссылаться на таблицы библиотек, наоборот — нет.

```go
{Name: outbox.MigrationsName, Table: outbox.MigrationsTable, FS: outbox.Migrations},
{Name: "service", Table: "schema_migrations", FS: migrations.FS},
```

Библиотека отдаёт `Migrations` (`fs.FS` со своими файлами по тем же правилам), `MigrationsName` и `MigrationsTable` (`<библиотека>_schema_migrations`), а сервис проверяет каждый источник из `MigrationSources()` по порядку на одной БД публичным `github.com/fin-assist/go-migrate/migratetest.CheckUpDownUp(t, dsn, source)` (`TestIntegrationUpDownUp` в `migrations/migrations_test.go`): новый источник проверяется без правки теста. Собственные тесты библиотеки определяются её README; сервис не копирует её test harness. Правило выпущенных миграций библиотеки — в её `docs/releasing.md`, «Миграции»: файл не меняется, несовместимое изменение схемы — в два выпуска.

## Изменение схемы без простоя

Сервис раскатывается на три реплики постепенно: какое-то время старый и новый код работают с одной схемой. Поэтому несовместимое изменение — в два релиза:

1. **Добавить**: новый столбец (nullable или с `DEFAULT`), новая таблица, новый индекс `CONCURRENTLY`. Код пишет в старое и новое, читает старое. Бэкфилл — отдельной миграцией или заданием порциями.
2. **Переключить** код на новое.
3. **Удалить** старое — следующим релизом, когда ни один под старой версии не работает. Down этого шага — ошибка «необратимо» (см. «Файлы»).

Переименование столбца или таблицы — это добавить + удалить, а не `RENAME`.

## Откат

- Сначала откатывается **приложение** — предыдущий образ работает со схемой после шага «добавить».
- `migrate down` — только для неудачного шага «добавить», когда новый столбец или таблица мешают и пустые: `bank-statement-data migrate down service 1`. Шаг «удалить» не откатывается — данные возвращаются из бэкапа.

## «Грязное» состояние

Миграция упала — источник остаётся `dirty` на её версии, и `migrate up` отказывается продолжать, пока человек не разберётся.

1. Посмотреть ошибку в логах Job или скрипта и `bank-statement-data migrate version`.
2. Проверить фактическую схему (`psql`, `\d table`) против up-файла. Обычно файл откатился целиком (неявная транзакция) — схема как до него. Исключение — `CONCURRENTLY`: может остаться `INVALID`-индекс, его удаляют вручную.
3. Выставить версию:
   - ничего не применилось — предыдущая версия: `bank-statement-data migrate force <source> <version − 1>`;
   - применилось всё (редко, например упал только `COMMIT`) — эта версия: `force <source> <version>`.
4. Исправить миграцию **новым** файлом или, если упавший файл ещё нигде не применён, исправить его в том же PR, и снова `migrate up`.

`force` делает владелец или дежурный: в проде — разовым Job с командой `migrate force …`, на стенде — тем же бинарём на сервере. В журнал инцидента — что было и какую версию выставили.

## Что можно в схеме

Решение владельца от 19.10.2026 ([FIN-194](https://finassist.youtrack.cloud/issue/FIN-194)): в схеме БД нет правил валидации и логики. Правило одно для сервисов и библиотек.

- **Можно:** `PRIMARY KEY`, `UNIQUE`, `FOREIGN KEY` с любыми действиями `ON DELETE` / `ON UPDATE` (включая `SET DEFAULT`), `NOT NULL`, `DEFAULT`, индексы — в том числе уникальные, частичные и по выражениям (`CREATE UNIQUE INDEX … ON t (lower(email)) WHERE deleted_at IS NULL`), генерируемые колонки `GENERATED ALWAYS AS (…) STORED` (значение, вычисленное для хранения или поиска, а не проверка). Identity-колонка (`GENERATED ALWAYS AS IDENTITY`) — отдельный случай, это ключ, тоже допустима.
- **Нельзя:** `CHECK`, `EXCLUDE`, триггеры, хранимые функции и процедуры, домены с ограничениями.
- Инварианты, которые раньше выражались бы так (диапазон, формат, взаимоисключающие поля, непересечение интервалов), проверяет код сервиса: правило — в `internal/domain` или в сценарии, с юнит-тестом на каждую ветку. Действия «по событию в таблице» (в том числе `pg_notify`) выполняет код сервиса в той же транзакции `db.Run`, что и запись.
- Инвариант между строками (бывший `EXCLUDE`, «одна активная запись», непересечение интервалов) выражается уникальным индексом, где это возможно (например, частичный `UNIQUE`), иначе проверяется кодом под блокировкой в той же `db.Run` — `SELECT … FOR UPDATE` родительской строки или транзакционная advisory-блокировка `pg_advisory_xact_lock(key)` (снимается на `COMMIT` / `ROLLBACK`; сеансовая `pg_advisory_lock` через пул осталась бы на соединении); такой инвариант покрывается интеграционным тестом с двумя параллельными писателями на PostgreSQL.
- **DDL внутри миграции — не рантайм-логика, допустимо:** `DO`-блок, который создаёт начальный набор партиций (см. «Партиции»), `RAISE EXCEPTION` в down-файле необратимого шага (см. «Файлы»). Такой код выполняется один раз при `migrate up` / `migrate down` и в схеме не остаётся.

Список инвариантов, которые проверяет код этого сервиса, и где именно, — [schema.md](schema.md), «Инварианты в коде сервиса».

Разрядность целого выбирается по диапазону значений и росту за срок жизни таблицы; для identity учитываются все выделенные значения последовательности, включая откаты и конфликтующие вставки. По [FIN-214](https://finassist.youtrack.cloud/issue/FIN-214) правило `prefer-bigint-over-int` выключено в `.squawk.toml`: `integer` не требует подавления. Правило `prefer-bigint-over-smallint` остаётся включённым; обоснованный `smallint` требует точечного `squawk-ignore` или `squawk-ignore-file`.

У каждой таблицы и каждого столбца — описание на русском: `COMMENT ON TABLE` (что хранит, ключ и роль) и `COMMENT ON COLUMN` (смысл значения). Описание начинается с русского слова; имена полей, коды и ссылки на контракт — внутри текста. У партиций `operation` описаний нет, их описывает родительская таблица. Таблицу или столбец без такого описания ловит `TestIntegrationEveryTableAndColumnHasDescription` (`migrations/schema_test.go`).

## Партиции

Ежегодные партиции `operation` (FIN-111) создаёт задание сервиса (Go-код), не миграция: миграции запускаются при деплое, а партиция нужна к дате. `pg_partman` не используем — его хранимые функции противоречат «Что можно в схеме» (FIN-194, решение владельца 19.10.2026). Первая миграция (`000001_init`) создаёт родительскую таблицу и партиции 2010–2027 (границы в UTC): выписка может уходить на годы назад, а операция вне всех партиций роняет импорт. Партиции `DEFAULT` нет — строка без партиции должна быть ошибкой, а не попадать в общую кучу, которую потом не разделить без блокировки. Задание, которое создаёт партицию следующего года, — [FIN-193](https://finassist.youtrack.cloud/issue/FIN-193); до него импорт операций 2028 года упадёт.

## Запросы на pgx

- **Два пула**: на primary (`DB_PRIMARY_DSN`, `-rw`) и на реплики (`DB_REPLICA_DSN`, `-ro`). Чтение после своей записи — с primary: `bank-bff` пробрасывает `x-read-primary`, `db.Reader(ctx)` выбирает пул по нему. На стенде оба DSN указывают на один PostgreSQL (или реплика не задана).
- **Только параметры** (`$1`, `$2`): ни одно значение из запроса не попадает в текст SQL. Имена таблиц и столбцов — константы в коде.
- **Таймауты**: `statement_timeout` на роль сервиса (`ALTER ROLE … SET statement_timeout`) и дедлайн контекста запроса; транзакции короткие, без внешних вызовов внутри.
- Транзакция — через адаптер `postgres.DB` общего менеджера `go-postgres v0.2.0`: `db.Run(ctx, func(ctx) error {…})`; репозитории берут её из контекста через `db.Writer(ctx)` / `db.Reader(ctx)`, библиотеки — через `db.Tx(ctx)` ([server.md](server.md), «Транзакции и чтение»).

### Нарушения ограничений и транзакции (FIN-195)

Общий механизм находится в `github.com/fin-assist/go-postgres` v0.2.0; `OpenPools` открывает пулы по переданным сервисом настройкам, `postgres.DB` остаётся тонким адаптером менеджера транзакций с выбором primary/replica. Usecase задаёт границы операции через собственный `Run`-интерфейс. Для операции с ожидаемыми нарушениями адаптер реализует этот интерфейс через `db.RunMapped(ctx, opts, mapper, fn)`.

Обработчик определён в адаптере **конкретной операции** и использует `go-postgres.IsViolation(err, SQLSTATE, constraint)`: проверяются и код, и имя ограничения. Он возвращает доменную ошибку без исходного `PgError` и его `Detail` либо `nil` для неизвестного случая (сохраняется исходная ошибка). Usecase переводит доменную ошибку в `finerr` по контракту: отсутствующий/чужой объект — `NOT_FOUND` или специальный код метода; `VALIDATION_ERROR` — только неверный формат. Для удаления родителя с зависимостями нужен код контракта; при отсутствии сначала изменить `contracts`. Неожиданное нарушение, например ключ, сформированный сервисом, остаётся внутренней ошибкой.

Репозитории внутри `RunMapped` возвращают ошибки запросов без доменного перевода: обработчик внешней операции увидит как ошибку callback, так и ошибку настоящего COMMIT. Это охватывает `DEFERRABLE INITIALLY DEFERRED` без `SET CONSTRAINTS ALL IMMEDIATE`: временно отсутствующий родитель может быть создан другим репозиторием до COMMIT. Для запроса вне транзакции есть `go-postgres.MapError`.

При нескольких репозиториях адаптер внешней операции явно выбирает ожидаемые нарушения; глобального реестра нет. Неоднозначное нарушение не переводится. Вложенный `Run` присоединяется к транзакции без COMMIT; его ошибки нужно возвращать наружу. Вложенный `RunMapped` с обработчиком отвергается до callback: обработчик должен принадлежать внешней операции. Опции вложенного `RunWith` игнорируются, действуют внешние. Контекст другого менеджера отвергается, Writer/Reader не уходят на свой пул в обход транзакции.

Проверяемый пример всех слоёв — `internal/adapter/postgres/transactions_test.go`: operation runner адаптера, интерфейсы usecase, доменная ошибка и `finerr.NOT_FOUND` после ошибки COMMIT. Библиотека не импортирует домен сервиса, контракты или `go-grpc/reqctx`.

Для новых миграций предлагаются явные имена `CONSTRAINT <name>` — на решение владельца. Существующие миграции и имена в рамках FIN-195 не меняются.

## Проверки в CI

- `go test ./...` с PostgreSQL в Docker (testcontainers): для каждой миграции сервиса — «вверх → вниз → вверх» на чистой базе (`migrations/migrations_test.go`), плюс тесты самого запуска.
- Squawk по **новым** up-файлам PR (`.squawk.toml`). Down-файлы проверяет «вверх → вниз → вверх».
- Существующие файлы в `migrations/` не меняются.

Локально без Docker — свой PostgreSQL:

```bash
# point the integration tests at a local server instead of a container
export TEST_DATABASE_URL='postgres://postgres@localhost:5432/postgres?sslmode=disable'
go test ./...
```

## Тестовая БД и публичный harness (FIN-258)

`internal/testdb` выбирает PostgreSQL18 через `TEST_DATABASE_URL` либо testcontainer. Публичный `go-migrate/migratetest.DSN(t, adminDSN)` создаёт отдельную БД и регистрирует bounded cleanup; helper не читает environment и не выбирает сервер. `migratetest.CheckUpDownUp(t, dsn, source)` проверяет переданный источник и не владеет lifetime БД. Существующие up/down файлы и тесты схемы сохраняются.

`internal/testdb` и `internal/app/apitest` остаются в одинаковом полном production-знаменателе трёх сервисных профилей. Библиотечное исключение `internal/pgtest` к сервису не применяется. Пулы primary/replica создаёт `go-postgres.OpenPools` v0.2.0, адаптер `postgres.DB` сохраняет routing и caller-owned transaction contract.
