# Версии и выпуск сервиса

`Release` публикует GitHub Release для существующего тега `vX.Y.Z` на коммите из истории `main`. Сборка и публикация образа, обновление стенда и deployment выполняются отдельно: наличие GitHub Release не означает, что сервис развёрнут. Workflow не создаёт и не переставляет теги.

Версия сервиса независима от версий Go-библиотек и контрактов, которые он импортирует. Публичным Go-модулем сервис не является: major-версия сервиса не требует суффикса `/vN` у пути в `go.mod`. Проверка совместимости API сервиса остаётся в контрактах и прикладных тестах; `gorelease` здесь не используется.

## CHANGELOG

`CHANGELOG.md` содержит сверху `## [Unreleased]`, далее — выпущенные версии по убыванию: `## [vX.Y.Z] — ГГГГ-ММ-ДД`. Секция версии содержит непустое описание изменений. Формат проверяют `python3 scripts/changelog.py check`, `make test` и CI. `python3 scripts/changelog.py notes vX.Y.Z` выводит текст раздела для GitHub Release.

Новый сервис начинает с пустого `[Unreleased]`: отсутствие секции версии не означает выпущенный `v0.1.0`. История прежних выпусков не выдумывается. Значимые изменения поведения, контракта, зависимостей и миграций описываются по-русски вместе с задачей FIN; инструкции миграции/раскатки нужны до выпуска. Внутреннее изменение CI без изменения приложения отдельной записи не требует.

## Выпуск

1. Подготовить PR выпуска с выбранной владельцем версией `vX.Y.Z`: перенести записи из `[Unreleased]` в датированную секцию версии и оставить сверху пустой `[Unreleased]`. Заголовок PR начинается с задачи FIN.
2. На чистом коммите выполнить `make test`, `make lint` и `make release-check VERSION=vX.Y.Z`. Дождаться ревью и успешного CI. Владелец сливает PR и проверяет post-merge CI нужного коммита `main`.
3. На проверенном коммите владелец ставит тег и отправляет его: `git tag vX.Y.Z && git push origin vX.Y.Z`. Агент теги не ставит, не удаляет и не переставляет.
4. `Release` читает файлы именно тега, проверяет формат версии, принадлежность коммита истории `main`, формат CHANGELOG и совпадение его новейшей секции с тегом. Затем создаёт GitHub Release с notes из этой секции.

Если GitHub Release уже существует, workflow успешно сохраняет его title, notes, assets и состояние публикации. Одновременное создание другим участником также допустимо. Если релиз не удалось ни создать, ни прочитать, workflow завершается ошибкой. Наличие Release не позволяет обойти валидацию тега и CHANGELOG.

## Повторная проверка

После исправления workflow запустить актуальное определение из `main` для существующего тега: `gh workflow run release.yml --ref main -f tag=vX.Y.Z` из локального клона нужного сервиса. Ручной запуск из другой ветки не выполняет job. Он всё равно читает CHANGELOG тега, а не текущего `main`; старый тег без правильной секции завершится ошибкой. Обычный rerun старого tag-run сохраняет старое определение workflow.

Опубликованные теги и применённые миграции неизменны. Ошибку исправляют следующим выпуском. Не создавать фиктивный тег для проверки CI: сценарии публикации, повторов и ошибок покрыты тестами настоящих shell-блоков workflow с Git и fake GitHub CLI.
